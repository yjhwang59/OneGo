# 競品觀察與分期規劃（草案）— PlayGo vs OneGo（OTC）

> 觀察來源：PlayGo 活動首頁（含活動分類、公告、付款型態與反詐宣導、歷史戰績/排行榜等）  
> 參考頁面：`https://tpego.hyplaygo.com/TPEGo/Home/Index3`

## 1. 功能對照表（PlayGo vs OneGo）

| 面向/功能 | PlayGo（從頁面可觀察） | OneGo（OTC）可精進方向 | 分期建議 |
|---|---|---|---|
| 多主辦單位（Organization） | 活動以不同單位分類展示（多主辦呈現明確） | 後台以 Organization 為租戶邊界：多主辦、多賽事、成員管理、資料隔離 | MVP |
| 主辦後台權限 | 有「主辦單位專區」入口（細節未見） | 組織層（Owner/Admin/Staff）+ 賽事層（TournamentRole：referee/staff）雙層 RBAC | MVP |
| 裁判/工作人員指派 | 未見規則（推測可指派） | 支援同一裁判指派多賽事，並做「賽事時間不重疊」檢查 | MVP |
| 活動/賽事查詢 | 有活動查詢、今日比賽一覽、精彩回顧分類 | 更強搜尋/篩選：棋種、地區、日期、賽制、主辦、狀態；可嵌入外部網站 | MVP/Next |
| 公告/維護資訊 | 有最新消息、維護公告（含付款維護） | 賽事/主辦/全站三層公告 + 排程化維護公告 + 訂閱通知（Email/Line/推播可選） | MVP/Next |
| 付款型態 | 明確提到以「永豐虛擬帳號轉帳」為主，無信用卡/儲值 | `PaymentProvider` 抽象：虛擬帳號/信用卡/行動支付/現場補繳；各賽事可開關 | Next |
| 反詐騙宣導 | 顯著位置宣導（禁止儲值、代辦退費等） | 產品化：付款頁/通知模板內建反詐文案、官方客服驗證碼、風險提示、操作稽核 | MVP/Next |
| 個資遮罩 | 平台顯示姓名遮罩 | 隱私分級：公開榜單/僅參賽者可見/未成年保護；可用代號/姓氏遮罩 | MVP |
| 多棋種支援 | 頁面多為圍棋（另有「五子棋、象棋及其他」分類） | 核心設計即多棋種：`GameKey + rulesetVersion + rules plugin`；同一流程套不同棋種規則 | MVP |
| 規則版本化 | 未見 | rulesetVersion 可逐步演進，不破壞既有賽事/歷史資料；可 A/B 測試不同輔分 | MVP/Next |
| 編排（Pairing） | 未見細節（推測有成熟編排） | 先做 MVP：第一輪隨機/種子；Next：Swiss/循環/淘汰（可插件化） | MVP/Next |
| 成績上傳 | 未見細節 | 結果上傳走狀態機事件；結果校驗/正規化由 rules plugin；支援作廢/更正與稽核 | MVP |
| 排名/輔分 | 公告提到「增加到第四輔分」等規則調整 | standings 純函式化 + 可設定輔分鏈（tiebreak pipeline），支援多棋種/多賽制 | Next |
| 歷史戰績/排行榜 | 有「個人歷史戰績」「年度排行榜」等指數查詢 | 跨棋種履歷：參賽曲線、對局歷史、勝率/常見對手、分棋種統計；可匯出 | Next |
| 行動端體驗 | 有 APP 下載（卡易通）與 Web 版 | 先做 PWA/響應式；Next 視需求做原生 App 或整合推播 | Next/Later |
| 對外 API/嵌入 | 未見 | 公開/授權 API：賽事列表、即時成績、精彩回顧；提供 embeddable widget | Next/Later |
| 稽核與合規 | 未見 | 全站 Audit log、敏感操作二次確認、異動差異比對、資料存取紀錄 | Next |

## 2. OneGo 分期（MVP / Next / Later）

### 2.1 MVP（先求「可用、可辦賽」）
- **多主辦單位**：Organization、成員角色、資料隔離
- **賽事核心**：Tournament（含狀態機）、Match、基本賽事時間（startsAt/endsAt）
- **報名/報到**：Registration、Check-in（含現場調整事件）
- **付款（Mock）**：建立付款單、標記成功/失敗（不耦合供應商）
- **編排（最小版）**：第一輪（或指定輪次）隨機/種子編排產生 Match
- **成績上傳**：Match result 上傳（rules plugin 校驗/正規化）
- **排名（最小版）**：以 rules plugin 的計分產生 standings（先不做複雜輔分鏈）
- **後台 MVP**：主辦能建賽事、管名單、報到、產生對局、輸入結果、查看排名

### 2.2 Next（差異化與擴展）
- **正式支付整合**：虛擬帳號、信用卡/行動支付（仍由 PaymentProvider 抽象）
- **編排擴充**：Swiss/循環/淘汰 + 作廢/重排流程更完整
- **輔分/同分判定**：可設定 tiebreak pipeline（含「第 N 輔分」擴充）
- **通知系統**：公告訂閱、對局通知、結果更新通知
- **稽核/權限細化**：Audit log、賽事層委派（臨時裁判）

### 2.3 Later（長期護城河）
- **即時系統**：現場即時看板、realtime 更新
- **更完整履歷/指數**：跨棋種排名、評級系統（視協會規則）、可視化報表
- **對外整合**：公開/授權 API、嵌入元件、第三方會籍/學校系統串接
- **行動端深度**：原生 App、離線優先、現場掃碼工作流

## 3. 開發時程（分期）與參考預算

> 下列為「參考」：會受 UI 深度、權限/稽核要求、支付整合複雜度、以及是否需要高可用/資安稽核而變動。  
> 我用最常見的兩種人力配置估算：**小隊（3–4 人）**與 **超精簡（1–2 人）**。

### 3.0 預設 MVP 範圍開關（本草案採用）
為了把「可辦賽 MVP」壓在可控工期內，本文件後續估算預設採用：
1. **支付**：**Mock Payment**（建立付款單 + 手動/測試事件標記成功/失敗），不做銀行/信用卡串接
2. **編排**：**簡易編排**（第一輪/指定輪次隨機或依種子），不做 Swiss/循環/淘汰完整規則
3. **公開性**：**半公開**（公開顯示代號/遮罩；詳細名單/聯絡資訊僅主辦與參賽者本人可見）

### 3.1 工期估算（以週為單位）
| 分期 | 交付物摘要 | 小隊（3–4 人） | 超精簡（1–2 人） |
|---|---|---:|---:|
| Phase 0（啟動） | 規劃定稿、DB/契約、Repo 骨架、CI | 1–2 週 | 2–3 週 |
| Phase 1（MVP API） | Organization + Tournament/Match + Registration/CheckIn + Mock Payment + 基本 Pairing/Result/Standings | 4–6 週 | 8–12 週 |
| Phase 2（MVP Web） | 主辦後台 MVP、參賽者查詢入口（報名/對局/成績） | 3–5 週 | 6–10 週 |
| Phase 3（Next 核心） | Swiss/循環/淘汰、tiebreak pipeline、通知、稽核 | 6–10 週 | 12–20 週 |
| Phase 4（支付整合） | 虛擬帳號/信用卡其一（含 webhook、對帳、退款流程） | 4–8 週 | 8–16 週 |

> **結論（常見落點）**：  
> - **可辦賽 MVP**：小隊約 8–12 週；超精簡約 14–22 週。  
> - **Next（含成熟編排/輔分/通知）**：再加 2–4 個月視範圍。

### 3.1.1 MVP 更精準拆解（以小隊 3–4 人為例）
- **第 1–2 週**：DB/契約定稿、Organization/RBAC 雛形、Tournament/Match CRUD、rules plugin 串接（結果校驗/正規化）
- **第 3–5 週**：Registration/Check-in、Mock Payment、Pairing（簡易）、Result 上傳、Standings（最小）
- **第 6–8 週**：主辦後台（建賽事/名單/報到/編排/輸入結果/排名）、參賽者入口（查詢）
- **第 9–12 週（緩衝）**：例外流程（退賽/作廢/更正）、隱私遮罩、可用性打磨、上線準備

### 3.2 參考預算（以「人月 × 單價」估算）
#### 3.2.1 人力需求（小隊建議）
- **後端**：1（API/DB/權限/支付抽象）
- **前端**：1（後台 + 參賽者入口）
- **產品/PM（可兼）**：0.5–1（需求、驗收、文件）
- **QA（可兼）**：0–1（測試流程、回歸）
- **UI/UX（可選）**：0–0.5（後台資訊架構、表單體驗）

#### 3.2.2 單價區間（台灣常見參考）
- **內部人力成本（含勞健保/管理費等粗估）**：每人月約 **NT$ 12–20 萬**
- **外包/接案人月（含溝通/管理與利潤）**：每人月約 **NT$ 20–35 萬**

#### 3.2.3 MVP 預算區間（粗估）
假設 MVP（Phase 0–2）合計：
- 小隊：約 **10–16 人月**（含 PM/QA 兼任與緩衝）
- 超精簡：約 **6–10 人月**（但時間拉長、風險較高、且 QA/PM 通常被擠壓）

對應預算：
- **內部人力**：約 **NT$ 120–320 萬**
- **外包/接案**：約 **NT$ 200–560 萬**

#### 3.2.4 Next 預算區間（粗估）
Phase 3–4（編排/輔分/通知 + 一種正式支付）合計：
- 小隊：再 **12–24 人月**
- 超精簡：再 **8–16 人月**

對應預算：
- **內部人力**：再 **NT$ 150–480 萬**
- **外包/接案**：再 **NT$ 240–840 萬**

## 4. 建議你下一步先決定的 3 個「範圍開關」
1. **支付**：MVP 先 Mock？或 MVP 就要上「虛擬帳號」？
2. **編排**：MVP 只做簡易編排？還是 MVP 就要 Swiss？
3. **公開性**：成績/名單是公開、半公開、還是僅參賽者可見？

## 5. 「一加就容易爆工期」的常見加項（估算增量）
> 下列為在 MVP 上「加回」能力時，常見的額外工期（小隊 3–4 人）：
- **正式支付（虛擬帳號或信用卡擇一）**：+4–8 週（webhook、對帳、退款、例外處理、客服工具）
- **Swiss 編排（含重排/bye/同分配對策略）**：+6–10 週
- **完整輔分鏈（可配置 tiebreak pipeline，含第 N 輔分）**：+4–8 週
- **通知系統（Email/Line/推播其中一種 + 訂閱/模板）**：+3–6 週
- **Audit log + 權限細化（含敏感操作二次確認）**：+3–6 週
