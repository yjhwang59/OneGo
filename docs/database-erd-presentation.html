資料模型切分

四個資料區塊

身份與權限 使用者、平台總管、主辦單位成員、賽事裁判與工作人員。 users
賽事核心 賽事本體、組別、輪次、桌次、雙方選手與結果。 tournaments
報名流程 報名、付款、報到，以 registration 作為流程主軸。 registrations
等級分系統 棋種設定、目前分數、歷史變化、計算任務。 ratings
核心方向：賽事流程與 rating 分開，降低耦合。

Core Tables

核心資料表職責

users所有參賽者、主辦、裁判與平台管理者的帳號主檔。
organizations主辦單位，也是目前多租戶資料邊界。
tournaments賽事本體：棋種、賽制、輪次、時間、狀態。
registrations使用者報名某場賽事，並可綁定組別。
matches單場對局資料，結果以 JSONB 儲存，由 rules package 校驗語意。
設計重點：Tournament 與 Match 是核心，付款與報到不侵入核心責任。

Registration Flow

報名、付款、報到

registrations一位使用者在同一賽事只能有一筆報名。
payments一筆報名可有多筆付款，支援重試與未來退款。
checkins一筆報名最多一筆報到資料。
資料庫已保護
`unique (tournament_id, user_id)` 防止重複報名；`checkins.registration_id unique` 防止重複報到列。

仍靠應用層
報名是否超過組別名額、付款成功後才可報到等流程規則。
流程主軸：registration -> payment/checkin
Rating System

ELO 等級分模組

rating_configs 每棋種一組設定，包含預設分、K 值、最低分與最高分。
player_ratings 每位玩家、每個棋種一筆目前分數，支援排行榜查詢。
rating_history 保留每次分數變化：賽事、對局、賽果、前後分數與 K 值。
rating_calculation_jobs 追蹤某場賽事的計算任務，避免完成後被重複計算。
rating.sql 依賴 otc.sql 已建立的 users、tournaments、matches。
Data Integrity

資料庫已經保護什麼？

唯一性組織 slug、email、Google sub、組織成員、賽事報名、組別 key、玩家棋種 rating。
父子關聯主辦到賽事、賽事到報名/對局、報名到付款/報到，多數已有 FK。
安全刪除部分資料 cascade，rating history 對賽事與對局採 set null，保留歷史分數。
基本檢查對局不可自己對自己，輪次必須大於 0。
狀態 enum賽事、對局、報名、付款、報到、棋種已使用 enum。
索引已有角色、組別、對局輪次、排行榜、rating history 查詢索引。
這些規則可降低髒資料進入核心流程的機率。
Risk Boundary

目前仍靠應用層保護

  • 組織角色、賽事角色、平台角色等 text 欄位合法值
  • `matches.player_a_id` / `player_b_id` 是否是有效參賽者
  • `category_key` 是否存在於該賽事組別
  • `matches.result` JSONB 是否符合棋種規則
  • 裁判跨賽事指派是否時間重疊
  • 組別 capacity 是否已滿
  • rating 完成後是否禁止重複入帳
這些不是錯誤，而是 MVP 常見的取捨。下一階段可以先補低成本的資料庫防線，再處理參賽者模型這類會影響長期演進的核心決策。
重點：區分「目前可接受」與「正式營運前應補強」。
Design Recommendations

建議優先順序

P0
  • 為 text 狀態欄位加 CHECK constraint
  • 限制 `matches.first_move` 只能是 A/B
  • finished match 必須有 result
  • 為 completed rating job 加 partial unique index
  • 補高頻查詢索引
P1
  • 強化 `category_key` 與 tournament_categories 的關聯
  • 明確 match player 來源：user、registration 或 participant
  • 建立 participants 表，支援退賽、替補、隊伍賽
  • `updated_at` 改由 trigger 統一處理
P2
  • 導入正式 migration 流程
  • 新增 payment events / refunds
  • 加入 audit log 與軟刪除
  • rating history 連到 calculation job
P0 先提高資料品質，P1 再處理模型演進。
Key Takeaway

結論

目前模型方向清楚：以 `organizations -> tournaments -> registrations/matches` 為主軸，權限分成平台、組織、賽事三層，rating 系統獨立在賽後計算。

短期補 constraint 與索引，快速降低髒資料風險。
中期建立 participants，讓配對、退賽、替補與成績更穩。
長期導入 migration、audit log 與完整付款事件紀錄。
